# Decoder fuzz campaign: tools and how to run it

This page describes the pieces that exist for the [decoder gate](../../spec/v0/conformance.md#gate.decoder) and what is still missing. It follows [the fuzz plan](../phase-0.5/decoder-fuzz-plan.md) and [the decoder contract](decoder-contract.md). Nothing here shows that the gate holds: the smoke run below is seconds long, and the release criteria need at least 250 CPU-hours per format with no open crash or confirmed hang.

## What exists

| Piece | Where | Notes |
|---|---|---|
| Fuzz targets | `crates/lumen-decoder/fuzz` | `decode_png`, `decode_jpeg`, `decode_webp` call the decoder as the worker does, with the worker's capped allocator; `reply_validate` drives the host's reply validation with arbitrary bytes and checks what it promises. Built with `cargo fuzz` on nightly, with AddressSanitizer. |
| Seeds | `cargo run -p lumen-decoder-tools --example seeds -- DIR` | Images from real encoders: PNG in 8 colour types and depths plus a 1 pixel image, JPEG in three sizes plus grayscale, WebP lossless with and without alpha. A test decodes every one with the real decoder. |
| Crash classifier | `decoder-fuzz-tools classify LOG` | Hang, memory, sanitizer, panic or other, from a libFuzzer log. Tested against excerpts of real logs in `crates/lumen-decoder-tools/tests/fixtures`. |
| Build identity | `decoder-fuzz-tools identity ROOT FLAGS` | SHA-256 over the decoder sources (not the test-only worker), its manifest, the lockfile, `rustc -vV` and the flags. |
| Campaign driver | `scripts/decoder-fuzz.sh` | Runs slices per format, keeps corpora, coverage samples and crashes, runs the G4 suite for the sandbox escape result and writes `ledger.json`. |
| Timeout triage | `scripts/decoder-triage-timeouts.py` | The campaign driver runs it after every slice and before the ledger. It replays each raw timeout record under the production limits (4 s wall, 2 s CPU, 512 MiB, two tries) and writes the verdict into `crashes.jsonl`: a record that stayed inside the limits is marked `"cleared": true` and is not open; a confirmed hang stays open. A failed replay clears nothing. |
| Ledger | `decoder-fuzz-tools ledger ...` | The format `lumen-evidence --decoder` reads. A test builds ledgers with these tools and has the real judge decide them. |

Run a short campaign and judge it:

```sh
NIGHTLY=nightly-YYYY-MM-DD scripts/decoder-fuzz.sh --out OUT --workers 2 --slice-seconds 20 --slices 2
cargo run -p lumen-evidence -- --decoder --ledger OUT/ledger.json --commit "$(git rev-parse HEAD)" --out OUT/evidence
```

CPU-hours are wall seconds times workers, summed over slices; that is an approximation of CPU time, not a measurement of it. A longer run is the same command with larger `--slice-seconds` and `--slices`; the output directory resumes.

## Findings so far

- **`png` 0.18.1 panics on a `PLTE` chunk whose length is not a multiple of 3** (slice index out of range in `create_rgba_palette`). The PNG fuzz target found 8 such inputs within minutes once the upstream regression seeds were in the corpus. The `png` crate skips its checksums under `cfg(fuzzing)`, so the raw inputs only fail in the fuzz build; with the CRCs repaired, 4 of the 8 panic the production worker, which exits 101 with no reply (the host reads that as a decoder crash and shows alt text, so it is contained). Upstream fixed it in image-png commit 8330c2c6 (2026-04-24), which is in no release; 0.18.1 (2026-02-14) is the latest. The worker rejects such files itself before calling `png` (`plte_lengths_ok` in `decode.rs`), and `tests/png_plte.rs` carries four repaired inputs plus a test that fails when `png` stops panicking on them, which is the cue to delete the workaround. After the check, the 8 original inputs run clean, and a further 300 s PNG run with 4 workers (about 0.33 CPU-hours, 8.1 million executions) found nothing; that is a smoke run and says nothing about the gate.

## Running it on a one-time spot VM

`scripts/decoder-fuzz-vm.sh` installs the toolchain on a fresh Debian or Ubuntu VM, checks out `COMMIT` and runs the campaign. The campaign is built to survive the VM disappearing:

- **State lives off the VM.** `--sync-cmd` copies the output directory (corpora, samples, crashes, crash inputs, replays, logs, ledger) somewhere durable after every slice, on SIGTERM and at the end. `--restore-cmd` brings it back on a replacement VM, and `--target-cpu-hours H` makes the same command continue until each format has H CPU-hours, however many VMs that takes.
- **A slice is the unit of loss, crash inputs are not.** A VM that vanishes without a signal loses the coverage sample and CPU-hours of the slice in progress, so slices are 900 s by default. Crash inputs are different: while a slice runs, the driver copies any new input the fuzzer writes into the output directory every 30 s (`ARTIFACT_POLL`) and syncs when there is one, and on resume it records any input the previous VM synced but did not get to record. A hard kill can still lose an input found in the last 30 s before it. Each copy is made under a temporary name, compared with its source and then renamed, so a copy that is cut off never leaves a truncated input under its real name for a later run to skip; a temporary file left by a killed copy is removed on the next run. A SIGTERM (the spot notice, a shutdown) stops the fuzzers, records the part of the slice libFuzzer reports, records any crash found, syncs, and exits 143.
- **A different build is refused, before it is restored.** The restore command runs against a staging directory (it sees that directory as `OUT`), whose commit and build identity are checked before anything is copied into the real output directory. A mismatch exits 3 and leaves the output directory as it was; its CPU-hours would not count for this build. The nightly is pinned in the VM script for the same reason.
- **A machine with no way out but its serial console.** `--checkpoint-console PATH` (normally `/dev/console`) writes, every `--checkpoint-minutes` (default 60) and once more at the end, one self-contained block of text lines: the build identity, each format's samples, crashes, state and rate, the slice log and, when they fit, the crash inputs. The launcher reads the console, and `--restore-console FILE` on a replacement machine takes the newest block in that text whose chunks are all present and whose SHA-256 matches (a block cut off by the console limit, or damaged, is skipped and an older one used), through the same staging directory and build check as `--restore-cmd`. **The limit: the corpus is not carried.** A block holds at most 17,000 bytes of state (about 26 KB as text, a bound the writer enforces whatever the words in its lines). One whole block is then inside any 64 KiB window of console text provided the other console output between two blocks stays under 13,500 bytes; with more output between them a window can hold no whole block, the reader finds nothing, and a restore exits 6 rather than use a damaged block. Status lines are a few hundred bytes a slice, so an hourly checkpoint stays well inside that. A corpus is far bigger than the block. A run restored from a block keeps its CPU-hours, samples and crash records, and starts its fuzzing from the seeds again, so its coverage can dip until the fuzzer finds its way back; the gate's coverage-plateau rule is judged on the samples, which carry over. If the crash inputs make a block too big they are left out of it (the crash records stay); if the records alone are too big, the checkpoint is reported as not fitting and the run goes on. The final results travel the same way, so they do not depend on a link that expires.
- **The VM ends itself only with the results safe.** `--finish-cmd` (for example `sudo shutdown -h now`, with the instance set to terminate on shutdown) runs after the ledger is written and a final sync has succeeded. If the final sync fails three times it does not run, the script exits 4, and the VM stays up with the results on it; that costs money, and it is the better failure.
- **One run per directory** (exit 5 if the lock is held).

`scripts/test-decoder-fuzz-spot.sh` tests these with real short fuzz runs: sync and finish on a normal run, a failing sync that blocks the finish command, a SIGTERM mid-slice, resume on a replacement directory from the synced copy, a refusal to resume a different build, and the lock. What it cannot test is the part that talks to AWS: the bootstrap's package and toolchain installation, and the real sync and shutdown commands. A short dry run on a throwaway VM (`TARGET_CPU_HOURS=0.02 SLICE_SECONDS=30`, with the real sync, restore and finish commands) would cover that for little money.

## The limits the fuzzer applies

- **Hang:** libFuzzer `-timeout=2`, the gate's 2 s.
- **Memory:** the targets use the worker's capped allocator, so an allocation that would take live bytes past 512 MiB aborts and is classified as memory. libFuzzer's own RSS limit is set to 2048 MiB as a runaway guard only, because it counts AddressSanitizer and corpus memory. Every `oom-*` artifact the fuzzer writes is replayed by the campaign script through the real worker (release build, no sanitizer, sandbox and limits on) with `scripts/decoder-replay.py`, which records the worker's peak resident size in `replays.jsonl`. The classifier reads that record: a peak over 512 MiB, or a worker aborted by its own heap cap, is a memory crash; anything smaller is recorded as an `asan-artifact` with its replay size and is not counted as a crash. The case that led to this: a smoke run with `-rss_limit_mb=512` reported "out-of-memory (used: 676Mb)" on a JPEG that declares 200 x 65280 pixels, and the replay script gave the real worker a peak of about 55 MiB for that input (`crates/lumen-decoder-tools/tests/fixtures/replay-oom-jpeg.json` is that record).
- **Residual limit of the memory check:** the allocator counts the Rust heap only. Memory mapped outside it (a library that calls `mmap` itself, thread stacks, the binary) is not counted by the cap. The replay's peak resident size would show it, but only for inputs the fuzzer reports as `oom-*`; an input that stays under libFuzzer's RSS limit is not replayed. In production the Linux address-space limit in the worker's sandbox covers all of it, and the fuzz run does not measure that.
- **The JPEG library is a release candidate.** `zune-jpeg` is pinned to =0.5.16-rc3 because 0.5.15 panics on malformed JPEGs: the JPEG fuzz target found 16 distinct inputs in under two CPU-hours, every one reproducing in the production worker (exit 101, no reply), and `tests/jpeg_panics.rs` keeps them. 0.5.16-rc3 answers all 16 without a panic. The memory-safety evidence was redone for rc3 itself, against the upstream source it was released from (the published package differs from it in one unused import); the committed record (the committed record next to the fuzz targets) lists every run. Passed in the interpreting checker with the vector code forced on: the library's unit tests, the same with default features, six of the fifteen integration test files, and the small seed JPEGs through the worker's decode path. Not passed, and recorded as such: the other nine integration files did not finish within ten minutes each there, which says nothing about the code either way, and the vector code for the Arm processor cannot run in the checker on the host used. One unit test compares the integer addresses of two function pointers, which is not stable: it passes in a native debug build and fails in a native release build and in the checker, on its assertion and not on a memory error, so it is skipped and run alone in the record. Those gaps are covered by native runs of the same tests on x86-64 and Arm, which pass (the PR thread has them). The crate has 89 lines containing `unsafe`, in 12 files. A move to 0.5.16 stable is a build change: it repeats this evidence and re-runs the gate.
- **Sanitizer and "UBSan":** AddressSanitizer reports count. Rust has no UBSan (`rustc -Zsanitizer` has no `undefined`). The fuzz build keeps overflow checks and debug assertions on (`[profile.release]` in `crates/lumen-decoder/fuzz/Cargo.toml`), so an arithmetic overflow or a failed assertion panics and counts as a crash; a test shows the classifier reads such a panic from a real log (`libfuzzer-overflow.log`, produced by a throwaway target). **This does not reach undefined behaviour inside `unsafe` code.** The decoders are not all safe Rust: `png` 0.18.1 and `image-webp` 0.2.4 forbid `unsafe` in their own code, but `zune-jpeg` 0.5.15 has about 87 lines mentioning `unsafe` in 13 files (counted with `grep`, so approximate), including the AVX2 and NEON inverse DCT, the upsampler and the bit reader. They are compiled in because the crate's default features `x86` and `neon` are on; without both the crate is `forbid(unsafe_code)`. Its dependencies add some more (`zune-core` 13 lines, and under `png` the `flate2` and `crc32fast` crates 36 and 15; which of those compile into the worker was not checked). ASan finds memory errors in that code when the fuzzer reaches them, but other undefined behaviour (aliasing, invalid values, misaligned access) is not seen by ASan or by overflow checks, and the fuzz run does not use Miri. Whether that is acceptable for the gate's "UBSan" line is a decision for the gate's owner; the ledger does not call it UBSan, and the build identity records `overflow-checks+debug-assertions (no UBSan for Rust)`. The gate run fuzzes the default-feature build under ASan, because that is the build that ships, with overflow checks and debug assertions on; Miri was run on `zune-jpeg`'s unsafe code as far as it can run (`scripts/decoder-miri.sh`, which writes `crates/lumen-decoder/fuzz/miri-record.json` from the logs; a later run can be checked against the committed record with `--compare`; the record and the hand-written `miri-gaps.json` are carried in the ledger's `notes`). Miri passed on the AVX2 code with no undefined behaviour: 10 unit tests, 17 integration tests (the slowest took 569 s) and this repository's small JPEG seeds, on x86_64 with AVX2 forced on, since Miri reports no AVX2 otherwise and would skip the code. **The NEON code has no Miri result**: Miri does not implement the intrinsics it uses on aarch64 and aborts. Nor did Miri follow the fuzzer's inputs; it ran the crate's tests and small seeds only. One option that removes most of the exposure: build `zune-jpeg` with default features off, which forbids `unsafe` in it, at the cost of the SIMD speed-up; that is not done here and would need the fuzz run and the performance to be checked on that build.

## Not done

> **The numbers moved.** The decoder gate in the specification no longer carries fuzzing quantities; they are in the [Lumen Term release criteria](../release-criteria.md#decoder-fuzzing). The judge (`lumen-evidence --decoder`), the campaign's gate status and the gate-run defaults apply that rule: a floor of 250 CPU-hours, and no open crash or confirmed hang for that build identity. The Lumen maintainers adopted it in place of an earlier coverage-plateau stop rule that the campaign never reached; the plateau is still recorded and reported and is not a condition. A raw timeout record that was replayed under the production limits and stayed inside them carries `"cleared": true` and is not open.

- **Past-CVE seeds.** None exist for the chosen libraries: the RustSec advisory database and GitHub's advisory database list no advisory for `png`, `image-webp`, `zune-jpeg` or `jpeg-decoder` (checked on 2026-10-29). What is included instead is `crates/lumen-decoder/fuzz/seeds-regression`: 31 inputs the upstream projects keep for bugs they fixed (16 PNG from `image-png`'s `tests/bugfixes`, 6 WebP from `image-webp`'s `tests/images/regression`, 9 JPEG from `zune-image`'s `test-images/jpeg`), each pinned by commit and listed with its size and SHA-256 in `MANIFEST.tsv`. The real decoder decodes 23 of them and rejects 8 as corrupt, with no panic (`tests/regression_seeds.rs`). These are regression inputs and not CVE reproducers. Seeds from CVEs in the C libraries for the same formats (for example libwebp's CVE-2023-4863) are not included: public reproducers vary in availability and licence, and committing exploit-shaped files is a choice for the gate's owner. If the gate reads "inputs from past CVEs" as satisfied by the empty set plus these, the ledger should say so; if not, those files have to be collected.
- **The terminal image path now exists, and the fuzz campaign did not cover it.** The image frames are parsed in `lumen-track0`, reassembled in order by `lumen-decoder` (`frames.rs`) and handed to the image manager, which the terminal drives and draws from. The campaign above ran the decoder targets on the guarded decoder build (the ledger's `decoder_build`) and did not fuzz the stateful frame, reassembly and drawing code, which was written after it. The image-path identity (`decoder-fuzz-tools identity ROOT FLAGS image-path`) hashes the host-side files of `lumen-decoder`, the parser, the layer, the terminal's image host, document and drawing files, the manifests, the lockfile, the compiler and the flags, so a change to any of them is a new image-path build whose gates have not passed. A pass of the decoder side is therefore not a pass of the image path, and the image frames are on by default but stay locked until a gate record for both identities is shipped with the build. A test fails if a source file of the decoder crate is in neither identity.
- **The image manager exists; the image frame does not.** `images.rs` holds what the spec fixes about images once their bytes have arrived: the unlock rule, the SSH rule, reserving `width * height * 4` before any decode, the 256 MiB session budget with 25% for an unsigned producer, 1 decode in flight per producer and 2 in total with 8 waiting, degrading a producer for the rest of the command after a crash or going over budget, and size-checking an upload against the 512 MiB texture budget before it is made. What it takes as input is an already-reassembled image with its producer, id, format and declared size. The v0 spec defines no image frame (no type byte, no payload, no chunking), so there is nothing to parse yet; that needs a spec decision first.
- **The identities are computed from the source tree, not embedded in the binary.** The unlock rule compares the identities the running build reports with the gate records it was shipped with; the build step that bakes the two identities into the terminal does not exist yet, and until it does the rule is tested against identities computed from a file tree.
- **Plateau.** The ledger records cumulative coverage edges and the judge reports whether they levelled off over the last 168 CPU-hours. It is information and not a condition of the gate. The guarded campaign below did not level off.
- **Platforms.** The gate is per platform. The smoke run was on macOS only, and the guarded campaign below ran on Linux only.
- **The floor of 250 CPU-hours per format.** The floor is met on Linux for JPEG and WebP on the guarded build (see the guarded campaign below), but that build is not the identity of the tree today, so it is not a pass for it. Not run for PNG on the guarded build or on any other platform. The plan's arithmetic is about one day of wall time on 32 cores for the floor and about five for the cap, for all three formats; the real number is whatever the ledger shows.

## What the smoke run showed

A two-slice run of 20 s with 2 workers on `png` and `webp` produced a ledger of 0.022 CPU-hours per format, edges 1537 to 1593 for PNG and 1178 to 1206 for WebP, no crashes, and the G4 suite at 33 of 33. `lumen-evidence --decoder` judged it `FAIL` (under the 250 CPU-hour floor). That is the expected result for a smoke run, and it shows the pieces fit together; it says nothing about the decoder's robustness.

## The guarded campaign

A campaign ran on Linux against the decoder build that includes the WebP guard. Runs on the earlier build do not count, because the guard changes the decoder build identity.

| Format | CPU-hours | Coverage edges | Crashes | Timeout records | Floor of 250 | Coverage levelled off (information) |
| --- | --- | --- | --- | --- | --- | --- |
| JPEG | 378.3 | 4309 | 0 panics | 930 | met | no |
| WebP | 411.8 | 4154 | 0 | 0 | met | no: the last sync still added an edge |

- **JPEG timeouts are not hangs.** Each of the 930 timeout records was replayed under the production limits (4 s wall, 2 s CPU, 512 MiB, two tries). The slowest took 0.73 s and used 153 MB, so none exceeded a limit.
- **The WebP guard is shipped.** `webp_guard.rs` checks the prefix codes before the library decodes them. An earlier run on the build without the guard found five inputs that overflowed in the library's Huffman code-length handling; the four crash inputs it kept answer with a clean refusal on the guarded build, and its 21 timeout inputs replay with no hang on both builds.
- **Why the runs stopped.** Both legs ended at their wall-clock limit. The campaign was then closed without more runs, so no ledger was judged.
- **The saved timeout inputs were replayed again.** All 945 saved JPEG timeout inputs (the campaign recorded 930 timeout records) were run one at a time through the production worker of the current tree (release build, sandbox on, its own limits, a 4 s wall limit). None timed out or exceeded a limit: the slowest took 0.69 s of wall time and 0.67 s of CPU, the largest peak was 149 MiB, and every worker answered with a decode or a clean refusal. So none of the JPEG timeout records is a confirmed hang. WebP recorded no crash on the guarded build, and the PNG run recorded none on its build.
- **Why this is not a gate record.** A record is written only against evidence for the identity of the tree it ships with. The campaign's decoder identity is not the current one: the decoder's sandbox source and its manifest changed afterwards (the Windows sandbox), and the image path has since gained the frame parser, the reassembly and the terminal's image host, none of which any run fuzzed. The PNG run (352 CPU-hours) is on the build before the WebP guard. All runs are on Linux. So no format has a pass for the current identities, and the image path stays locked until the runs for them exist.
