## Not backwards compatible, by design

Lumen is a new protocol rather than another escape-code extension. Grid blocks give existing terminal apps a native place inside a Lumen document, and unverified output is always shown as plain, inert text.

## Status

`lumen-term` has a native window backend behind the off-by-default `window` feature. It is implemented and tested on Linux, macOS and Windows, and a real native window was captured on each: Linux under X11 on a virtual display, macOS in a clean virtual machine, and Windows on a dedicated test profile. None of these was a physical display.

The current public draft is **Lumen Protocol v0, revision 25 (frozen snapshot)**. It is not stable, and breaking changes are expected. [Read the spec](@/spec/v0/_index.md). The decisions behind it and the risks accepted are on the [decisions page](@/decisions.md).

Lumen is in Phase 0.5. The Lumen maintainers adopted Arm B for v0: Track 0 rich everywhere, with the sealed upgrade, and multiplexer panes keep the sealed relay. The evidence, and what is not yet measured, is in [the decision record](https://github.com/moonbase2090/lumen/blob/main/docs/phase-0.5/decision.md).


Phase 1 has started on Arm B. The terminal runs programs on the upstream VT core and draws the trust margin itself. A sandboxed image decoder and an image manager enforce the image rules. Both are connected to the terminal: its image host calls the image manager and decodes out of process. Images are on by default, on Linux and macOS (Windows is unsupported for images in v0 and shows the alt text). The unlock rule still applies: a build shows an image only when gate records exist for both of its build identities, and the shipped records do, so the terminal shows the image, and the setting `images = false` always shows the alt text. [Lumen Term's release criteria](https://github.com/moonbase2090/lumen/blob/main/docs/release-criteria.md) set the decoder fuzzing gate. Each image format must reach at least 250 CPU-hours on each platform for both the decoder build identity and the terminal image-path build identity, with no open crash or confirmed hang. The Lumen maintainers adopted this rule in place of an earlier coverage-plateau stop rule that the campaign never reached. An open crash fails that build identity. Fuzzing continues after release, and every decoder version bump requires another run. Status: met for the current build identities on the basis of an accepted carry-forward. The maintainers counted the guarded fuzz runs (PNG 352, JPEG 378 and WebP 412 CPU-hours, no open crash or confirmed hang) as the decoder gate for the current decoder and image-path identities on Linux and macOS, with no new fuzzing. Those runs were on Linux and on earlier identities: the decoder's sandbox and manifest changed afterwards, and the frame parser and image host were never fuzzed. This is an accepted residual risk, listed on the decisions page, and the next decoder bump needs its own fuzzing. The JPEG run's 930 timeouts were replayed again under the production limits and none was a hang. The WebP guard, which checks prefix codes before the library decodes them, is shipped. The JPEG decoder is pinned to zune-jpeg 0.5.16-rc3, a release candidate: 0.5.15, the last stable release, panics on 16 malformed JPEGs found by fuzzing, and rc3 answers all of them without a panic. Those inputs are now regression tests. Because this changes the decoder build identity, an earlier fuzzing pass for JPEG covered only the earlier identity; the maintainers' carry-forward above accepts it for the current one, and a later bump must be fuzzed again. A grid parser drops string escapes. The notification path in the window draws sealed notifications as toasts, and a click dismisses a drawn toast. An operating-system backend is implemented and tested on Linux, but the window does not yet show a notification from a real program. Notification settings read only from the user's policy file. A Linux sealing probe and a key-holder shell accept messages only from the terminal's shell. The key-holder shell can receive a layer's key, but nothing in the terminal sends one yet. No layer seals yet. Paragraph and heading text keeps zero-width characters (ZWJ, ZWNJ and variation selectors), ZWSP and WJ act only as line-break controls, and bidirectional controls are closed at every line and block end. These rules are now on by default; a build without default features keeps the earlier rules. Where the terminal composes text a person relies on to judge trust (notifications, link labels and targets, the code-block language label), invisible and bidi code points show as visible escapes such as ⟨U+200B⟩. When typed input cannot be sent because the program is not reading it (or has ended), the window says so with a notice the terminal draws in the notification area, never in the trust margin, and counts what was dropped. A budget model, `lumen-budget`, holds the numbers of the resource-limits table (the pooled document budgets with the local reserve and the producer and unsigned shares, the per-second rates and the limits on a single item, including the largest legal image of 16 megapixels) with language-neutral test vectors run against it; nothing in the terminal calls it yet, so these limits are not newly enforced. Nothing here is released. The progress is listed in the [README](https://github.com/moonbase2090/lumen#status).
