## Not backwards compatible, by design

Lumen is a new protocol rather than another escape-code extension. Grid blocks give existing terminal apps a native place inside a Lumen document, and unverified output is always shown as plain, inert text.

</section>

## Status

`lumen-term` has a native window backend behind the off-by-default `window` feature. It is implemented and tested on Linux, macOS and Windows, and a real native window was captured on each: Linux under X11 on a virtual display, macOS in a clean virtual machine, and Windows on a dedicated test profile. None of these was a physical display.

The current public draft is **Lumen Protocol v0, revision 25 (frozen snapshot)**. It is not stable, and breaking changes are expected. [Read the spec](@/spec/v0/_index.md). The decisions behind it and the risks accepted are on the [decisions page](@/decisions.md).

### Phase 1 progress

Phase 1 is current on Arm B. The terminal runs programs on the upstream VT core and draws the trust margin itself. A sandboxed image decoder and an image manager enforce the image rules. Both are connected to the terminal: its image host calls the image manager and decodes out of process. Images are on by default, on Linux and macOS (Windows is unsupported for images in v0 and shows the alt text).

The unlock rule still applies: a build shows an image only when gate records exist for both of its build identities. The shipped records do, so the terminal shows the image, and the setting `images = false` always shows the alt text. [Lumen Term's release criteria](https://github.com/moonbase2090/lumen/blob/main/docs/release-criteria.md) set the decoder fuzzing gate. Each image format must reach at least 250 CPU-hours on each platform for both the decoder build identity and the terminal image-path build identity, with no open crash or confirmed hang. The Lumen maintainers adopted this rule in place of an earlier coverage-plateau stop rule that the campaign never reached. An open crash fails that build identity. Fuzzing continues after release.

Status: image testing is complete. The gate records for the current decoder and image-path identities are committed, and images are on by default on Linux and macOS. The guarded fuzz runs (PNG 352, JPEG 378 and WebP 412 CPU-hours, no open crash or confirmed hang) were on Linux and on earlier builds: the decoder's sandbox and manifest changed afterwards, and the frame parser and image host were not fuzzed.

The JPEG run's 930 timeouts were replayed again under the production limits and none was a hang. The WebP guard, which checks prefix codes before the library decodes them, is shipped. The JPEG decoder is pinned to zune-jpeg 0.5.16-rc3, a release candidate: 0.5.15, the last stable release, panics on 16 malformed JPEGs found by fuzzing, and rc3 answers all of them without a panic. Those inputs are now regression tests. Because this changes the decoder build identity, the earlier JPEG fuzzing covers only the earlier identity.

Bright can open several independent windows and restores the size, position and zoom of each on its next launch. Command+N opens a window on macOS; Control+Shift+N does so elsewhere. Each window can hold several tabs, each with its own program and program-set title. A terminal-drawn row names the tabs and marks the active one; clicking another tab switches to it. A tab can be split into panes, each with its own program, side by side or stacked: Split Right and Split Down (Command+D and Command+Shift+D on macOS, Control+Shift+D and Control+Shift+E elsewhere) divide the focused pane in two, and the new pane takes the focus; Next Pane and Previous Pane (Command+] and Command+[ on macOS, Control+Shift+. and Control+Shift+, elsewhere) move the focus around the panes in reading order, and a click focuses the pane it lands in. Keys, paste, the input method and Find go to the focused pane, the wheel to the pane under the pointer, and a drag that began in a pane stays in it. A divider line separates the panes and a bar of the accent colour marks the top of the focused one. Dragging a divider resizes the panes on either side of it as the pointer moves, and stops where a pane would go below 20 columns by 5 rows; a press inside a pane still focuses it, and the panes keep their shares when the window is resized or zoomed. Close (Command+W, Control+Shift+W) closes the focused pane, and the tab with its last pane; a pane whose program ends closes by itself and its neighbour takes the space. A pane is not split below 20 columns by 5 rows, zoom applies to all the panes of a tab, and the split layout is not kept between launches. A screen reader is told which pane of how many has the focus. The window has actions of its own, from a menu item or a shortcut: create, switch and close tabs; split a tab into panes and move between them; copy the selected text, paste the clipboard text, select all; make text larger or smaller or return it to the display's size; and quit. On macOS the tab chords are Command+T, Command+Shift+[ and Command+Shift+], and Command+W; the other actions use the usual Command chords, and the menu bar carries the same tab actions. Settings, or Command+comma, opens the settings file with its default app and creates a starter with the defaults when the file is absent. Theme, font, copy-on-select and smooth-scrolling changes in the settings file apply to every open tab within a quarter second; shell settings apply to tabs opened afterwards. On Linux and Windows there is no menu: Control+Shift+T creates a tab, Control+Shift+[ and Control+Shift+] switch, and Control+Shift+W closes it; the other window actions use Control+Shift chords, so no plain Control key a program uses is taken. On Linux, Control+Shift+S or Settings in the right-click menu opens the settings file with its default app, creating the starter first when the file is absent and never replacing one that exists; when it cannot be opened the window shows a notice saying why. A line sent from the input box at a shell prompt is the shell's now: keys typed right after its Enter, before the shell has read it, go to the shell as typeahead and not into the box, and the box takes keys again once the tty shows the shell has run the line and is back at its prompt (or after 300 ms when the shell is never seen leaving). Ctrl+C does not wait. Paste goes through the paste rules. At a shell prompt a paste lands in the input box with its line breaks kept, and nothing runs until Enter. If the shell takes bracketed paste, Enter sends the lines as one command between the paste markers; if not, Enter asks: Enter sends them as separate commands, J joins them into one line, and Esc cancels. In a program that is reading keys itself, when it has turned on bracketed paste the text goes in between the paste markers, line breaks kept, with the escape and control characters and a pasted end marker removed; otherwise text with a line break or a control goes in as one line. Text carrying a frame introducer is refused either way. Dragging the pointer over the text selects it, in the grid and across the wrapped lines of a rich block; a copy of wrapped text comes back as one line, with the blank the wrap dropped kept as a space, and a program that asked for mouse reports gets the pointer unless Shift is held. The reports use the SGR encoding when the program asked for it (DECSET 1006) and the default encoding when it asked for tracking alone (DECSET 1000, 1002 or 1003); that encoding cannot name a cell past column 223, so a press there is not sent, nor is the rest of that click, while a drag or release that ends there is reported at the last cell it can name. Reports and bracketed paste go only while the program that asked for them is still in front of the terminal: after it exits or another program takes the terminal, a paste goes in without paste markers and the pointer selects text again. On Linux a finished mouse selection also becomes the primary selection, whatever the copy-on-select setting, and a middle click pastes it through the same paste rules as Paste; a program that asked for mouse reports gets the middle click unless Shift is held. Selecting by keyboard, by word or by line, and selecting inside a strip are not there yet.

Typing updates the input box as you type. Program output appears as it arrives, even while the pointer stays still. Output is kept and scrolls. Until output has scrolled, the screen takes only the rows it has used, so rich blocks a program writes, and the prompt after them, stay in view instead of being pushed up by empty rows below the cursor. The wheel moves the view three rows a step, easing there over a few frames (typing, a page move, a find or a zoom end the easing at once; setting `smooth_scroll = false` in the settings file makes each step jump instead; so does the system's own request for less motion, which is macOS Reduce motion or GNOME's animations switched off, checked when the window starts and each time it gains focus), a trackpad moves it by the distance it travelled, and Page Up and Page Down move it a page. Shift or Control with Home and End go to the oldest output and back to the newest. Scrolling up holds the place: new output arrives below it and does not move what you are reading, and a thin bar at the right edge shows where you are. A program's last 1000 rows of output are kept; once they are full, new output drops the oldest rows, and a view scrolled up moves with them so it keeps showing the same text, then stays at the oldest output left if the rows it showed have gone. Typing, or reaching the bottom again, returns to the newest output. A program that asked for the wheel, or that is on the alternate screen (an editor, a pager), keeps those keys and the wheel for itself.

A grid parser drops string escapes. The notification path in the window draws sealed notifications as toasts, and a click dismisses a drawn toast. An operating-system backend is implemented and tested on Linux, but the window does not yet show a notification from a real program. Notification settings read only from the user's policy file. The spec now defines when a layer may count as local for notifications: only when the terminal started it and can bind every foreground process to this machine with credentials it owns, re-checked on every process-group change and before any unsigned toast or OS notification. It fails closed, and no platform has a reviewed probe yet, so every layer is still treated as not local.

Find looks through everything the window shows or keeps: grid output including its scrollback, and the text of rich blocks. Command+F on macOS, or Control+Shift+F elsewhere, opens a bar across the top of the output; what you type is searched as you type, ignoring case, and every match is highlighted, the current one in a stronger colour with an outline. Enter or Command+G (Control+Shift+G, or F3) goes to the next match and Shift+Enter or Command+Shift+G (Shift+F3) to the previous one, wrapping at the ends, and the view scrolls to bring the match into sight. The bar shows which match you are on and how many there are. While it is open your typing goes to the bar, not the program; Escape closes it and takes the highlights away, and the next Find, or Find Next or Previous, searches for the same text again. A line the terminal wrapped is one line for the search, so a match can run from the end of one row to the start of the next and is highlighted on both; a real line break still separates lines. New output is searched as it arrives without moving the view.

The window works with the system's input methods, dead keys and compose sequences. Text an input method commits reaches the program once, as typed text, with control characters removed so it cannot carry an escape sequence; a dead key or compose sequence arrives as the letter it makes. While a composition is unfinished the program sees nothing, and losing focus or turning the input method off drops it. On macOS, Option with a key that makes an accented or other non-ASCII letter sends that letter, not an Escape prefix. The text being composed is drawn where it will go, underlined: inline at the caret of the input box (the rest of the line moves right), or at the program's cursor while the program has the keys, with the clause the input method has selected underlined more heavily. It is clipped to the box or the window, and drawn dimmer when the window is not focused. The system's candidate window sits at the same place and follows the window as it is resized or zoomed. In the input box, the candidate window stays aligned with the caret after wide characters. Clicking within a wide character puts the caret at its start. Chinese, Japanese and Korean characters the monospace face lacks are drawn from a bundled fallback face covering the common characters of those scripts, two cells wide.

The window shows the title a program sets with OSC 0 or OSC 2 in its own title bar, never in the page, followed by the terminal's name, as in `build log - Bright`. An empty or blank title, or none at all, shows the name alone. A title with a control character is refused whole, bidirectional controls are removed, and a long title is cut so the name stays last.

The window follows the display it is on: when it moves to a display with a different scale factor, text is drawn again at that display's own scale (rounded to a whole number, up to 4), so it stays sharp, the program is told its new window size, and a zoom you made stays the same number of steps from the display's scale. A scale set with the `--scale` option is kept as set. A fractional factor such as 1.5 is drawn at the nearest whole scale. The question about a link and the menu the terminal draws on Linux are drawn at the largest size, no smaller than the display's own scale, at which they fit the window both ways, so zooming to three or four times never pushes an address, a button or a menu entry out of the window or out of the pointer's reach; they follow the palette when it changes. When even that size is too small for a long address, the question shows it a page at a time (Up and Down, Page Up and Page Down, or the wheel move it, and the last line of the box says which lines are shown) with Open and Cancel always in view. The menu does the same (the wheel and the arrow keys move the page), and in a window too narrow for the two buttons side by side they go one above the other. Each window's zoom is kept between launches, as a number of steps from the display's own size, and a window comes back at its own zoom; Zoom Reset still goes back to the display's size.

When a program rings the bell while the window is not focused, the window asks the system for attention once, with no text and no icon of the program's own: the dock icon bounces on macOS when Bright is run as the installed application (a bare executable started from a shell has no dock icon of its own to bounce), and the taskbar entry or the window is marked on other systems. It takes the request back when the window is focused again, and a new request waits a few seconds after the last, so a program that rings in a loop cannot make it strobe. A bell that ends a title or another string is not a bell, and nothing is drawn in the page.

Selecting text with the mouse copies it to the system clipboard when the button is released, the same copy the copy command makes, so the same rules apply. Only a selection Bright made itself is copied: a program that asked for mouse reports gets the clicks and nothing is selected (hold Shift to select: with Shift held the program is sent neither the press nor the release, only the terminal selects), a click with no drag copies nothing, and select all waits for the copy command. Setting `copy_on_select = false` in the settings file turns it off.

A right click opens a context menu with Copy, Paste, Select All and the zoom items, the same actions as the menu bar and the shortcuts; on Linux it also offers Settings, last. A right click on a link adds Open Link and Copy Address at the top, on the grid and on a web address written in a rich block's text, where an address the block wrapped over lines is offered whole from each of them. Both ask first, in the terminal's own question that shows the whole target and warns when the text shown looks like a different address: Open Link opens only after a yes, and Copy Address copies the checked address the question showed, never the text the link displays. They are turned off for a `file:` link and for a target the terminal refuses. On macOS and Windows it is the system's own menu; on Linux the terminal draws it, over everything a program can draw, and it works with the pointer (a press on an entry chooses it; a press elsewhere closes it) and with Up, Down, Enter and Escape, while no key reaches the program until it is closed. The drawn menu is a raised surface with a control edge; the highlighted entry is filled with the accent colour and its label drawn in the canvas colour, so it stays readable in every built-in palette, high contrast included. Copy is turned off when nothing is selected and Paste when the clipboard holds no text. A program that asked for mouse reports gets the right click itself; hold Shift to open the menu instead.

On Windows the window opens with no console window behind it. Because the program has no console of its own, the text the command line options print, such as the usage text and the settings summary from `--show-settings`, does not appear in a terminal unless the output is redirected to a file or a pipe (`lumen-term --show-settings > settings.txt`).

A web address written in a program's output is a link, in the scrollback as well as on the screen. On the primary screen and in its scrollback, an address the terminal soft-wraps stays one link across the rows: every part is underlined and asks with the full target. A real line break keeps addresses separate. It is underlined in the accent colour, and holding Control (Command on macOS) while pressing the primary button on it asks before anything happens. The keyboard reaches links too: Next Link and Previous Link (Command+L and Command+Shift+L on macOS, Control+Shift+L and Control+Shift+K elsewhere) move a focus through the links on the screen in reading order, wrapping, and show the focused link selected; Enter asks about it exactly as the press does, and Escape or any other key lets go. The question is drawn by the terminal, above everything a program can draw: it shows the whole address, with the host in ASCII form and never cut, says that the address was found in the program's output, and has Open and Cancel buttons, drawn as controls with an edge and labelled in the body text colour, which Enter and Escape also answer. The press, the keys, the wheel (a line wheel or a trackpad) and the window's own paste, find and zoom actions go to the question, not to the program, and nothing opens until you choose Open. Only `https` and `http` addresses are found in text, and an address longer than 2048 characters is not a link; an address with a user name in it is shown and not opened. A link a program sets with the OSC 8 escape is a link too, in the scrollback as well as on the screen, underlined and asked about the same way. Its text can say anything, so the question shows the target the program set, never the text, with the text the link covers on a line of its own and the words "Set by the program"; it warns when the text reads like a different address. The same rules apply to the target: a target that is not `https`, `http` or `mailto` is explained and not opened (a `file` target is only shown, with its path to copy), one with a user name in it is not opened, and one over 2048 bytes, or with parameters over 256 bytes or with a control character in them, is not a link and ends any link before it. Setting a link never opens anything or reaches the shell; only your choice of Open does.

On Linux, a listed zsh that the terminal starts directly can have a sealed layer. The terminal creates the seal channel first, starts the shell with a shim and that channel, and starts the holder and delivers a key only when the sealing conditions say to seal. The holder then seals a command start, a prompt boundary or a command end when that shell asks, and refuses every other request, including from a program the shell starts. If the decision is not to seal, or the holder cannot start, the shell still runs and the layer stays grid-only, with no holder and no key, and the window says so in a notice that names the failed check. On a sealed layer the input box takes keys only once the shell has said, in a sealed frame, that it is at a prompt: a shell builtin that reads keys itself, such as `read -k`, gets them, and keys typed before the shell has answered an Enter stay with the shell's next line instead of being split between the box and the shell. A line you are writing in the box stays there while the shell's prompt hook runs a program: keys typed meanwhile finish that line in the box and do not go to the program. At every Enter it forwards, the terminal checks that the shell has not executed another program; a layer that fails the check, or whose holder ends, is grid-only from then on, and the window shows a notice that says why. Both notices are the terminal's own text, stay until dismissed, and go when the shell ends. Lines sent as separate commands, or pasted with line breaks into a program that does not take bracketed paste, go one at a time: each waits until the shell is back at its prompt and passes the check again, and lines that cannot be sent come back to the box unsent. For each sealed command, the terminal keeps the line the box sent whole for it, with the exit status from the shell's sealed command end. It is a record of what was typed, not of what ran: an alias or history expansion is not reflected, and a line handed to the shell's own editor, or keys a running command read, are not recorded. On a sealed layer Up recalls those lines, so a line the shell refused to run is not offered again; a layer without keys recalls the box's own history. When the command starts, the line the box's line was sent on (that row and any the terminal wrapped it on to) has to show the whole of it; if a line typed ahead ran there first, or the shell drew the line its own way, the box's line is not recorded for it. On a sealed layer, a short `kbd` mark in the gutter, which only the terminal draws, sits beside the row each such line starts on; with the pointer over it, it says "typed here", and a click puts the line back in the input box, unsent. A layer without keys shows no marks, and its gutter is drawn two cells wide instead of four, so a program there is given two more columns in the same window; when a layer gains or loses its keys, the program is told the new width. The header strip above the content carries no title. Clearing or resetting the screen, or changing the window's width, drops them; a change of height, such as the input box growing or shrinking, keeps them. macOS and other systems stay grid-only.

In a rich block, paragraph, heading and image alt text is now drawn in a proportional face (IBM Plex Sans) laid out by each glyph's own width and wrapped at the block's pixel width, instead of on the monospace grid; code blocks, grids, toasts and the trust margin stay on the grid. A character the proportional face lacks, or one that takes two cells, is drawn from the monospace face. Tests run on Linux and macOS check the glyph widths, and a real-window capture from a clean macOS guest is in the repository. Headings are set larger than the body, one size per level, and the container's "unverified output" label one size smaller; the container has padding inside its edge and a margin outside it. The window keeps a margin clear to the right of the text, where the scroll bar sits, and below the last row.

Paragraph and heading text keeps zero-width characters (ZWJ, ZWNJ and variation selectors), ZWSP and WJ act only as line-break controls, and bidirectional controls are closed at every line and block end. These rules are now on by default; a build without default features keeps the earlier rules. Where the terminal composes text a person relies on to judge trust (notifications, link labels and targets, the code-block language label), invisible and bidi code points show as visible escapes such as ⟨U+200B⟩. When typed input cannot be sent because the program is not reading it (or has ended), the window says so with a notice the terminal draws in the notification area, never in the trust margin, and counts what was dropped.

The terminal's colours come from a design system with light, dark and high-contrast palettes, each checked against its own contrast floors. The window follows the system's light or dark appearance by default and switches live, with no restart. A settings file read at start chooses a fixed palette or a theme file (a built-in palette with colours changed, refused whole if any text would fall under the 3:1 visibility floor), and the face and size of monospace text and of prose, and the shell to run. With no program named, the window runs the `shell` setting, then `SHELL`; failing both, PowerShell (`pwsh`, then `powershell`), then `cmd.exe` on Windows, and `/bin/sh` elsewhere. A file that cannot be used is left out with a notice and its default applies. There is no in-app picker yet.

The window draws the cursor of the program's live screen as the program set it: block, underline or bar, blinking or steady, shown or hidden. A blinking cursor restarts its cycle on a key, pasted or composed text, or output, and an unfocused window draws it dimmed and steady, with a block as an outline. When the system asks for less motion the cursor does not blink.

When the system asks for more contrast (macOS Increase contrast, a GNOME desktop's high-contrast setting, a Windows High Contrast theme), a look that follows the system draws the built-in high-contrast palette at once and goes back when the system stops asking; a palette fixed in the settings file is kept. The terminal reads the answer when the window opens and when it gains focus. A text selection redraws what it covers on the palette's selection colour, with the text in one colour of its own (so a colour a program gave the text is not kept while it is selected); that pair holds the same text floor as the rest of each built-in palette. A theme file can set both with `selection` and `selection_text`. Pictures and emoji in a selection are tinted instead.

On macOS and Windows the window tells a screen reader what it shows, through the platform's accessibility API. The terminal is a text area whose children are the rows the window shows, as text, and the links in them, each with its address: a reader that acts on a link gets the same question a press gets, with the whole address and Open and Cancel buttons, and nothing opens until it is answered. The keyboard's focused link is the reader's focus. With more than one tab the tabs are a list that marks the active one, and in a split tab the terminal's name says which pane of how many has the focus. The terminal is marked as a polite live region; what a screen reader announces as the screen scrolls has not been checked. The tree is built only while a screen reader is connected. Linux does not tell a screen reader anything yet.

A budget model, `lumen-budget`, holds the numbers of the resource-limits table (the pooled document budgets with the local reserve and the producer and unsigned shares, the per-second rates and the limits on a single item, including the largest legal image of 16 megapixels) with language-neutral test vectors run against it; nothing in the terminal calls it yet, so these limits are not newly enforced. Nothing here is released. The progress is listed in the [README](https://github.com/moonbase2090/lumen#status).
